## 一、阻断项（Blocking Issues）

### B1：收藏/关注连续快速取消两条后再撤销其中一条时，错撤对象、列表顺序颠倒，且与 D8a `FavoriteRepository` 缓存可能失步

- **文件与行号**：
  - `hipda/src/main/java/net/jejer/hipda/feature/mine/FavoritesPane.kt:36-44`
  - `hipda/src/main/java/net/jejer/hipda/feature/mine/FavoritesViewModel.kt:50-52, 85-113, 120-123, 135-139`
  - `hipda/src/test/java/net/jejer/hipda/feature/mine/MinePagesBehaviorTest.kt:151-225`
- **具体触发路径**：
  1. **触发路径 1（Snackbar 串行挂起阻塞导致错撤对象、D8a 缓存恢复错条目）**：
     - 初始列表为 `[7001, 7002, 7003]`（D8a `favoriteTids == {"7001", "7002", "7003"}`）。用户先点取消 `7001`，紧接着（10 秒内）点取消 `7002`。
     - D8a `FavoriteRepository` 已依次移除两条，`favoriteTids` 变为 `{"7003"}`。
     - 但 `FavoritesPane.kt:36-41` 在 `viewModel.snackbarEvents.collect` 内直接调用挂起函数 `snackbar.show(...)`（带「撤销」按钮时为 `SnackbarDuration.Long`，`SnackbarHostState.showSnackbar` 挂起约 10 秒），第二次 `Removed(7002)` 事件被阻塞在 `SharedFlow` 缓冲区中，屏幕上仍显示绑定到第一条 `7001` 的 Snackbar。
     - 用户点击「撤销」预期恢复刚取消的 `7002`，实际却调用了 `restoreItem(..., 7001, 0)`，将 `7001` 写回 UI 与 D8a `FavoriteCacheStore`（`favoriteTids` 变成 `{"7001", "7003"}`，而刚点的 `7002` 仍处于被取消态），随后才弹出滞后的第二条 Snackbar。
     - 此外，`FavoritesViewModel.kt:91-92` 仅在网络 `favoriteRepository.remove` 返回后才发出 `Removed` 事件；若第一次 `7001` 的 Snackbar 已显示，用户点取消 `7002`（UI 已乐观移除）并在 `remove(7002)` HTTP 飞行途中点屏幕上的「撤销」，同样会错撤 `7001`。
  2. **触发路径 2（可变列表裸下标 `originalIndex` 重插导致顺序颠倒）**：
     - 初始列表 `[7001, 7002, 7003]`：先点取消第 2 条 `7002`（`FavoritesViewModel.kt:86` 记录瞬时下标 `idx = 1`，列表变 `[7001, 7003]`），紧接着点取消第 1 条 `7001`（列表变 `[7003]`）。
     - 当对 `7002` 执行 `restoreItem`（或 `remove(7002)` 网络报错回滚）时，`reinsert`（`FavoritesViewModel.kt:135-139`）在 `size = 1` 的 `[7003]` 上计算 `1.coerceIn(0, 1) == 1`，执行 `list.add(1, 7002)`，列表变为 **`[7003, 7002]`**，与原相对顺序 `[7002, 7003]` 颠倒。
     - 反之若先取消 `7001`（`idx = 0`）再取消 `7002`（在 `[7002, 7003]` 中 `idx` 也记为 `0`），两条依次回滚/撤销后列表变为 **`[7002, 7001, 7003]`**，前两条顺序颠倒。
  3. **触发路径 3（并发刷新及跨栏操作下 UI 列表与 D8a `FavoriteRepository` 缓存不一致）**：
     - `FavoritesViewModel` 未订阅对齐 `favoriteRepository.favoriteTids` / `attentionTids`，且 `loadPage`（`:120-123`）未对本地未决移除做过滤：当 `getList` 刷新请求飞行中用户点击取消 `7001`（D8a `DefaultFavoriteRepository` 完成移除并递增 `kindMutationVersion`，拒绝将旧页 `7001` 合并回 `FavoriteCacheStore`，此时 `isFavorite("7001") == false`），随后旧 `getList` 返回时，`FavoritesViewModel.kt:121-123` 仍直接将含 `7001` 的旧列表覆盖回 UI，造成 UI 显示仍在收藏而 D8a 仓库缓存已移除；在三栏/详情页跨组件取消收藏或关注时，列表同样不会随 `favoriteTids`/`attentionTids` 同步剔除。
     - 测试 `MinePagesBehaviorTest.favoritesAndAttention_removeAndUndoRestoresViaMockWebServer` 仅验证了单条取消后立即撤销，未覆盖连续快速取消两条后再撤销其中一条的场景。
- **修复建议**：
  1. 在 `FavoritesViewModel` 为每个 `FavoriteKind` 记录条目首次加载时的单调顺序秩（`orderRank: Map<String, Int>`），`reinsert` 按原始秩插入到第一个 `rank > itemRank` 的元素之前（而非依赖可变裸下标 `originalIndex`），确保任意子集以任意顺序撤销或失败回滚都不乱序；
  2. 点击取消时立即切入最新一条的可撤销态（`FavoritesPane` 用 `collectLatest` 收集 `snackbarEvents`，新操作立即取消并替换上一条未决 Snackbar；若 `remove` 网络请求失败则发出错误事件覆盖撤销条并按秩回滚）；同一 `(kind, tid)` 的 `remove` / `add` 在 ViewModel 层按发起顺序串行执行，避免快速「取消 → 撤销」在进入仓库锁前乱序；
  3. 订阅 `favoriteRepository.favoriteTids` / `attentionTids`（结合本地未决恢复/移除集合）过滤已不在 D8a 缓存中的条目，并在 `MinePagesBehaviorTest` 增加 `MockWebServer` + `DefaultFavoriteRepository` 下「连续快速取消两条（含正序与逆序）后再撤销其中一条」对列表顺序与 `favoriteTids`/`FavoriteCacheStore` 一致性的断言。

### B2：浏览历史与最近搜索的 Undo Snackbar 串行挂起阻塞，导致连续删除或「单删后紧接清空」再点撤销时回滚错目标

- **文件与行号**：
  - `hipda/src/main/java/net/jejer/hipda/feature/mine/BrowseHistoryPane.kt:36-42`
  - `hipda/src/main/java/net/jejer/hipda/feature/search/SearchPane.kt:69-77`
- **具体触发路径**：
  1. **浏览历史（`BrowseHistoryPane.kt:37-40`）**：Room 中有 `[e1, e2, e3]` 时，用户先点删除 `e2`（触发 `snackbar.show("已删除", ..., "撤销")`，`collect` 协程挂起约 10 秒），1 秒内再点顶栏「清空」（`clearAll()` 立即执行 `dao.trimTo(0)` 删空 `[e1, e3]`，页面变为 `暂无浏览历史`）。此时用户点屏幕上的「撤销」欲恢复刚清空的历史，实际执行的却是上一条挂起未退场的 `restoreItems([e2])`，刚被清空的 `[e1, e3]` 未被写回 Room，且紧接着又弹出第二条 Snackbar。连续单删两条（如先删 `e2` 再删 `e1`）后点「撤销」同样会错撤 `e2`。
  2. **最近搜索（`SearchPane.kt:70-75`）**：最近搜索 `["折叠屏", "键盘", "咖啡"]` 中连续快速删除 `"折叠屏"` 与 `"键盘"` 后点「撤销」，因 `collect` 挂起在第一条 `"折叠屏"` 的 `snackbar.show` 上，实际恢复的是第一条 `"折叠屏"` 而非刚删的 `"键盘"`。
- **修复建议**：
  - `BrowseHistoryPane.kt` 与 `SearchPane.kt` 将 `viewModel.snackbarEvents.collect` 改为 `collectLatest`（与 B1 一致：新删除/清空事件到达时立即取消上一条 `showSnackbar` 协程并展示最新一次删除/清空的「撤销」），并补充连续删除 / 单删后立即「清空」再点「撤销」的自动化测试（验证最新一次删除或清空的 Room 记录含 `lastVisitedAt` 与排序完整恢复）。
