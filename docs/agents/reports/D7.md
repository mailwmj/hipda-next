## 二、核心设计与关键取舍说明

### 2.1 `inajax=1` 发送端点改用 D2 `isUnauthenticated` 谓词替代 `requireAuth = false` 的取舍
- **采用方案**：`DefaultSmsRepository.sendSms` 第 1 步 GET `pm.php?daterange=1&uid=...` 保持 `requireAuth = true`（默认 `#umenu` 谓词）并通过 `DiscuzCommonParser.parseFormhash` 严格校验表单 `<input>`（避免误取 `#umenu` 退出链接 `formhash`）；第 2 步 POST `pm.php?action=send&pmsubmit=yes&infloat=yes&inajax=1`（按 UID 附 `&uid={uid}`，按用户名表单附 `msgto`）采用 D2 修复轮新增 API：`forumHttpClient.postGbkForm(..., requireAuth = true, isUnauthenticated = ::isSmsAjaxUnauthenticated)`。
- **谓词防误判设计（`DefaultSmsRepository.isSmsAjaxUnauthenticated`）**：
  1. 先经 `B9a` `SmsParser.parseSmsSendResult` 解析：若为 `SmsSendResult.Success`（含 `class="summary"`），**直接短路返回 `false`**，确保用户发送正文中包含“您还未登录”等字样被回显时绝不误触发静默重登与重复发信；
  2. 若返回业务拒绝 XML（如“收件人不存在”“两次发送短消息间隔太短”），返回 `false`，零多余重登请求，映射为 `SmsSendOutcome.Rejected`；
  3. 仅当解析失败文本命中 Discuz! 7.2 显式未登录提示（`您还未登录`/`您尚未登录`/`尚未登录`/`请先登录`/`您需要先登录`/`无权进行当前操作`）或意外回落到无登录态完整 HTML 页时返回 `true`，交由 `ForumHttpClient` 复用单飞静默重登 + 可重放 GBK 表单最多重试 1 次。
- **取舍评估**：
  - **收益**：闭合了第 1 步预取与第 2 步 POST 之间的会话过期竞态窗口；正常成功/业务拒绝 XML 仍保持与 `requireAuth = false` 完全一致的 0 额外请求开销；无法恢复的鉴权失败自动由 `ForumHttpClient` 转为 `AuthRequiredException` → `SmsSendOutcome.AuthRequired`。
  - **已知局限**：`ForumHttpClient.postGbkForm` 重试会重放第 1 步取到的同一份表单 `formhash`。Discuz! 7.2 同账号静默重登通常保持 `formhash` 有效；极端情况下若服务端轮换 `saltkey` 或跨时间窗导致 `formhash` 失效，重试将返回 `SmsSendOutcome.Rejected`，且不会锁定 15 秒冷却，上层 `E8` 可直接原地重发并重新预取 `formhash`。

### 2.2 短消息 15 秒冷却与并发防重入
- 使用 `Mutex`（`sendMutex`）串行化 `sendSms`，冷却校验与发送在锁内完成：冷却未满直接返回 `SmsSendOutcome.CooldownActive(remainingSeconds)`，发起 **0 次网络请求**。
- 剩余秒数遵循 `product-design.md §7.3` **向上取整**：`((remainingMs + 999L) / 1_000L).toInt()`（`0ms → 0`，`1..1000ms → 1`，`14_001..15_000ms → 15`）。
- 仅当 `SmsSendResult.Success` 时记录发送时间并开启 `15_000L` ms 冷却；参数非法、缺 `formhash`、服务端拒绝、鉴权失败、验证失败与网络异常均不触发冷却（遵循 `product-design.md §7.5`）。
- 账号切换或退出登录时重置冷却并防止旧账号在途成功响应误锁新账号冷却。

### 2.3 分离未读流、本地按条/全部已读持久化与账号隔离
- **严格分离的双未读数流**：`NotifyRepository.smsUnreadCount: StateFlow<Int>` 与 `NotifyRepository.notifyUnreadCount: StateFlow<Int>` 独立维护，互不混加，满足 `_reports/D-3pane.md` §5 与 `BATCH-4.md` §1.4 三栏左栏契约。
- **确定性提醒键（`NotifyEntry.computeKey`）**：基于 `kind`、`tid`、`pid`、`authorUid`、`author`、`time`、`title`、`info` 做长度前缀编码后取 SHA-256 前 128 位（`${kind.name}:<32hex>`），刻意排除会随服务端刷新翻转的 `isNew` 及会随 `forumServer` 变化的 `avatarUrl`，同时避免 `SYSTEM`/`FRIEND` 缺 `tid`/`pid`/`time` 撞键。
- **不因加载 `notice.php` 误清未读**：加载 `notice.php` 仅与 `NotifyReadStateStore` 已读键集合合并并持久化未读键列表，未打开条目保持 `isRead = false`；跨实例重启、后续刷新 `notice.php`（即使服务端撤掉 `notice_newpm.gif`）及 `updateFromPageMeta(PromptCounts(0))` / `pollUnreadCounts` 均不会将未打开的本地提醒清零。
- **全量已读水位与容量裁剪**：`NotifyReadStateStore` 使用独立非加密 `notify_read_state.preferences_pb`（`ReplaceFileCorruptionHandler { emptyPreferences() }` + 读流 `IOException` 兜底 + 损坏 JSON / 错类型回退），按 `ownerUid` 分键存储，已读键集合保尾去重并裁剪至上限 `500` 条；在未加载 `notice.php` 前触发 `markAllNotificationsRead()` 时持久化 `suppressedServerNotifyCount` 水位，避免旧页头计数反复回弹，待新提醒到达（计数超出水位）或访问 `notice.php` 后自动恢复。
- **冷启动水合与切换/退出隔离**：区分冷启动首次水合（`null → A`）与显式退出（`A → null`）/ 切换账号（`A → B`）：退出与切换立即递增 `accountGeneration` 并将内存双未读流与列表清零，丢弃旧账号在途请求并阻止退出态残留回调复活旧计数。

### 2.4 面向 `D9` 的 `pollUnreadCounts` 轮询入口
- `pollUnreadCounts(priority)` 经 `ForumHttpClient.getHtml("pm.php?filter=newpm", priority = priority, requireAuth = true)` 原样透传 `AccessPriority`：
  - 同一响应同时解析 `SmsParser.parseSmsList`（更新 `smsUnreadCount`，仅当未读数为 `1` 时带出 `latestUnreadSms` 预览）与 `meta.promptCounts`（与本地未读提醒协调计算 `notifyUnreadCount`）；
  - 同时捕获直接抛出的 `ChallengeAbandonedException` 与 `AuthRequiredException(RELOGIN_FAILED, SilentReloginResult.Failed(CHALLENGE_ABANDONED))`，统一映射为 `NotificationPollResult.ChallengeAbandoned` 且**不修改既有未读数**、不触发 `ChallengeSolver`。
